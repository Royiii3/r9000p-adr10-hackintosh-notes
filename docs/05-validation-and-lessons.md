## 1. 每个阶段只验收它真正证明的东西

| 看到的现象 | 可以说明 | 还不能说明 |

## 2. CPU 和 GPU 分开验收

本次最大的误导是“画面出来了，CPU 名称也像很多核心”。实际审计只有一个逻辑处理器在线。

`cpus=1` 可以成为排障阶段的有效条件，但它是很大的性能限制，不应被包装为最终优化。移除限制后出现 Panic，也不应反过来把显卡此前的真实测试全部否定。

同样，Metal 正常不等于 Chromium 的 WebGL/WebGPU 正常。本机报告记录原生计算和渲染通过，内置 Chromium 的 WebGL 上下文创建失败、WebGPU adapter 为空。只改应用级图形选项需要独立 A/B，不能随手全局关闭安全机制。

## 3. 把每次开机当成一次有编号的实验

反复重启一次可能消耗十几分钟，最不值得做的是重启后才发现不知道选了哪个入口、改过什么或脚本到底有没有运行。

重启前留一条短记录：

```text
实验：CPU-12
设备：按本机可核对的物理身份记录，不只写盘符
启动入口：Macintosh HD
配置基线：能进桌面的 cpus=1
唯一修改：cpus=1 -> cpus=12
成功标准：能登录、读取真实在线数量、无新 Panic
失败时保留：完整照片 / Panic 文件 / 对应配置
回退：已备份的 cpus=1 配置
```

下一次回来先写结果，再开始新修改。不要一轮里同时换显卡版本、改核心数、换一套 ACPI、关校验、改分辨率。

## 4. 只在有问题要回答时收集日志

OpenCore 日志重点在引导器阶段，不能假设它记录了 macOS 内核之后的所有事情。本次 RELEASE 文件可能预分配 256KiB，实际只有一行或没有正文；文件大不表示有完整日志。

macOS 内部卡住时，要找正确进程名。本机真实进程曾为 `Language Chooser`，中间有空格，只匹配 `LanguageChooser` 会漏采。普通用户无法读取部分系统进程采样时，要保留权限错误，不能把没拿到日志说成进程没运行。

可以优先看版本、实际 kext、boot-args、CPU、对应崩溃报告，再决定要不要采样。`cpus=1` 的初次图形会话已经很吃力，不宜同时自动跑大量 profiler、着色器测试和长日志查询。

## 5. 校验和备份要有目的

本次旧 U 盘的直接重复读取试验回答了“是否读到稳定字节”，并有 SSD 对照，值得做。官方安装器的包完整性检查也有明确用途。

但在每次修改小参数时重复全量哈希、把一切异常都说成“文件冲突”、为防万一批量删备份，并不能提高诊断质量。先保留一个明确可启动的基线，再做有理由的最小检查。

没有被引用的旧目录、根目录脚本、旧压缩包不会仅因为在 U 盘上就自动运行。真正需要检查的是默认启动路径、固件选择、`startup.nsh`、当前配置引用和启用的任务。

## 6. AI 能协助，但不能替代重启后的证据

这次 Windows 和 macOS 两端都用过 Codex。它们能分析配置、准备脚本和整理日志，但会话之间不一定共享最新状态：一端不知道另一端为什么保留 `cpus=1`，就可能再次移除限制；脚本写好了，也可能被误读为实际已经装好了。

有用的交接文档应写：当前活动配置在哪里、哪些参数有失败历史、原始报告在哪里、下一轮允许改哪一项、哪些操作只是准备没有执行。本次在 U 盘审计报告末尾写 `reply` 就是为了交接这类事实。

公开经验中也要保留失误：曾把已安装驱动的 IONDRVSupport 屏蔽带进恢复配置；曾用恢复系统没有的命令；曾只根据配置落盘谈“修复”。这些都比只给一份看起来整洁的 EFI 更值得后人知道。

## 7. 为什么最后停止

单逻辑处理器下已能展示不少功能，但多核、外设和稳定性还没过关。反复等待和重启的投入已经超过我愿意继续付出的时间，于是删除系统，把空间还给 D 盘。

本次不是对整个黑苹果路线或任何上游项目的最终判决。后人可以继续，但应先定好自己的验收目标和停止条件：是体验桌面、开发测试，还是要一个每天依赖的系统。这些目标需要的可靠性不一样。
