# 故障、处理和没有证明的事情

[返回首页](../README.md) · [完整流程](02-installation.md)

下面保留错误原文和判断边界。很多阶段叠加过多轮修改，不能把“后来进去了”全部归功于最后看到的一行参数。

## 1. OpenCore 只有 Windows，没有 Recovery

**现象：** 已进入 OpenCore 菜单，只能看到 Windows，空格没有带出 macOS 恢复入口。

**检查顺序：**

1. 先确认启动 U 盘的物理身份和全部分区，不根据盘符猜。
2. 确认分区根目录存在 `com.apple.recovery.boot`。
3. 同目录存在配套的 `BaseSystem.dmg`、`BaseSystem.chunklist`，没有只复制 EFI。
4. 核对 `ScanPolicy`、`HideAuxiliary` 和启用的文件系统驱动。
5. 核对 HFS+/APFS/OpenRuntime 的文件、路径和启用状态。
6. 阅读本次启动日志，区分没扫描到、扫描到但隐藏、扫描到了但镜像加载失败。

**本次边界：** 后来恢复入口出现，但现有材料不能把最初只显示 Windows 的情况归结为一个已独立证明的单点原因。不要为了写一个干净故事而补造“原来就是某文件缺失”。

## 2. `DMG has been altered` / `LoadImage Failed - Unsupported`

镜像名和大小正确，也可能读出来的字节不稳定。

旧 U 盘上曾发生这些错误。后续绕过 Windows 文件缓存，在 DMG 的 28 个位置各读两次、每次 1MiB：

| 对象 | 抽样结果 |
|---|---|
| 旧 U 盘，原接口 | 28 个位置中 22 个两次读取不一致 |
| 旧 U 盘，另一个直连 USB 接口 | 28 个位置中 14 个不一致 |
| 内置 SSD 上的镜像对照 | 28 个位置重复读取全部一致 |
| 新 SanDisk 的 DMG | 28 个位置稳定且与本地原始文件一致 |
| 新 SanDisk 的 2.3.4 包 | 8 个位置稳定且与本地原始文件一致 |

**已确认：** 旧 U 盘恢复镜像所在读取链路异常；换接口没有消除。

**没确认：** 是闪存、控制器、供电、接口还是其他底层因素；也没有证明每个 EFI 小文件都坏了。22 和 14 是抽样结果，不是故障率或硬件寿命测量。

`chkdsk` 没发现文件系统错误，不能排除这种问题。把镜像重新复制一次、改文件名、删备份、关闭签名校验，都不能解释或修复底层重复读取不一致。

## 3. 早期 type 14 Page Fault，以及 15/26 对照

早期照片包含 `CR2=0xFF00004C` 一类故障地址。实际运行时内存图中，OpenCore 对 `0xFF000000` 开始的区域执行了 MMIO 去虚拟化。

处理思路是保留整体去虚拟化设置，只把**对应本机映射**的 `0xFF000000` 区域加入白名单。后续不再停留在同一个早期阶段，但没有完成严格的反复开关对照。

15 恢复环境也曾在早期崩溃，因此“都是 26 的原因，换 15 就一定好”没有成立。反过来，这也不能说明所有 15 和 26 的问题都相同。

MMIO 白名单必须来自自己的固件映射和故障证据。不要把本机地址当成所有 Zen 4 笔记本必填项。

## 4. 停在 `PCI configuration begin` / `PCI0`

曾停在这一阶段超过五分钟，也有一次等了半小时。

本机检查过：

- Zen 4 的 IOPCIFamily 补丁是否齐全、启用、与当前 Darwin 范围匹配。
- 16 核核心数补丁是否为 `0x10`。
- `ResizeAppleGpuBars` 与 `ResizeGpuBars`。
- `npci=0x2000` / `npci=0x3000` 是否存在，是否与已确认的 BIOS 设置冲突。
- SSDT、重命名和依赖是否存在明显错误。
- 恢复阶段是否误用了已安装 NVIDIA 的配置。

一次在启用可选 `IOPCIIsHotplugPort` 补丁后进入恢复图形界面。这是值得记录的关联，但不是证明所有 ADR10 都需要该补丁。

后来重装时又发现 IONDRVSupport Exclude 仍开着，违反上游对恢复安装阶段的配置要求，予以纠正。日志仅出现 `Exclude ... Unsupported`，而这行也出现在能够进入系统的启动里，所以不能称它已证明是唯一原因。

**屏幕最后打印 PCI0，不足以断定正在执行的阻塞恰好就在那一行。** 异步初始化、没有继续输出、图形切换失败都可能让最后可见行留在那里。没有内核堆栈或进一步证据时，保留未知。

Above 4G 状态没有可靠读取，不能凭空说“已开”或“没开”；本次不把添加 `npci` 作为无条件通用修复。

## 5. `OpenRuntime.efi at 2 cannot be found!`

```text
OC: Driver OpenRuntime.efi at 2 cannot be found!
Halting on critical error
```

这发生在 UEFI 驱动加载阶段，不等于 Macintosh HD 的安装内容坏了。`at 2` 是配置中驱动的零起始序号，不是磁盘 2。

检查时发现：

- 文件实际存在于 `EFI/OC/Drivers/OpenRuntime.efi`。
- `UEFI/Drivers` 引用和 Enabled 正确。
- BOOTx64、OpenCore、OpenRuntime 与当时同版本 DEBUG 发布包匹配。
- 没有发现它被重命名、删除或与另一版本混用的证据。

当时只从匹配来源刷新了同内容 OpenRuntime 文件，保留引用，没有重新生成 EFI。因为刷新前内容本身正确，不能把这次处理写成“确认找回丢失驱动”。启动来源或介质读取是候选解释，未独立证实。

## 6. 菜单选择后等约 300 秒

用户多次反馈按数字后要等四五分钟，好像键盘死了。日志中确实出现过接近第 300 秒才开始镜像相关处理的记录。

后续将同提交的这三个核心文件作为一组从 DEBUG 切换到 RELEASE：

```text
EFI/BOOT/BOOTx64.efi
EFI/OC/OpenCore.efi
EFI/OC/Drivers/OpenRuntime.efi
```

配置没有随这次构建切换一起重做。用户明确反馈“一按就进去了”，这是本次有实机反馈的改善。

不能进一步说：所有 DEBUG 都固定等待 300 秒、旧 U 盘无影响、所有 UEFI 键盘问题都修好了。后期旧盘读取异常是另一份独立证据。

另一个常见误解是看见 boot-args 中 `debug=0x100` 就以为又用了 DEBUG OpenCore。它们不是一回事。

## 7. 菜单键盘、macOS 键盘、触控板要分开

OpenCore 菜单还没启动 macOS，不能用 VoodooPS2/VoodooI2C 是否安装来解释该阶段所有按键问题。NumLock 灯能亮也不足以证明菜单一定收到了方向键。

进入 macOS 后，则要检查 PS2/I2C/HID 驱动绑定、重复 VoodooInput 插件、ACPI、USB 控制器和端口等。日志中 I2C 某些 timing property 缺失，并不单独证明它们就是整机卡住的原因。

这台机器后期键盘和触控板可以使用，但没有完成全部键位、组合键和三四指手势验收。USBToolBox + UTBDefault 也不等于本机物理端口已经完整定制。

## 8. 黑屏只剩可移动鼠标

这说明图形会话至少走到了一定阶段，但不能确认 Metal 加速、WindowServer 合成、Setup Assistant 或显示模式全部正常。

尝试过低分辨率，仍然黑屏；后来恢复到 Max。不能把“降低分辨率”写成已经验证的修复。

有时驱动根本还没执行安装，有时四个驱动已加载为 2.3.4 后仍卡住。判断应使用：

1. 安装任务日志是否真的执行完。
2. `/Library/NullMoth/driver-version` 写的是什么。
3. 重启后四个 kext **实际加载**的版本。
4. WindowServer / Setup Assistant 的进程、采样和崩溃报告。
5. Metal/显存/实际渲染结果。

不能把一个“关于本机”窗口、可移动鼠标或版本文本代替这五层检查。

## 9. 国家选择后转圈、白屏、迟迟不继续

有过以下日志：

```text
mostFrequent countries found: (null)
scannedCountryInfos: ()
failed to do a bootstrap look-up ... com.apple.dock.fullscreen
Dock connection error: Connection invalid
```

这些确实发生在卡住的会话中，但没有证明是地区数据库损坏、Dock 必须重装或系统完全死锁。可能只是没有获得地区推荐数据，或初始化会话里缺少某个服务连接。

一次早期快照记录 CPU 空闲为 0、可用内存约 27GB；WindowServer 多个线程在 NVMTL/Vulkan/NAK 的着色器编译和管线创建中。它支持“当时有明显负载”，不能凭三秒采样宣布永久死锁，也不能说所有卡顿只由 `cpus=1` 引起。

最后通过创建普通账户、设密码、写完成标记绕过，进入桌面。**这是绕过初始化瓶颈，不是修复了这些服务的已证实根因。**

## 10. 恢复终端脚本报 `shasum: command not found`

恢复系统不是完整 macOS，不能假设 Python、Perl、shasum、开发工具或所有用户态命令都在。

本次早期脚本因为缺少 `shasum` 把后续检查判成“配置改变”。这是工具不可用，不是配置一定遭篡改。后来的安装方式是在恢复环境中暂存任务，到已安装系统里执行官方安装器主体。

文件校验应服务于下载损坏、来源或介质故障这类具体问题。不要在每次只改一项参数时反复对整个 EFI 或数百 MB 包全量校验，增加等待却没有新增判断价值。上游安装器自己的完整性检查是另一回事。

## 11. “更新了”但版本还是旧的

必须区分：下载了、复制到 U 盘了、写了待执行任务、安装器实际执行了、重启后新内核驱动真正加载了。

本次准备过 2.4.3，但不能据此说本机运行了 2.4.3。后期有日志和加载记录支持的版本是 2.3.4。升级后若还显示旧 kext，需看 AuxKC 构建和实际加载路径，不能只覆盖一个版本号文件。

## 12. 显卡能显示、能跑测试，为什么还是没留下来

GPU 加速的某些路径通过，不代表整个系统日用可接受。多核启动没有通过，内置音频、无线、蓝牙、背光和浏览器图形接口仍有缺口。对本次使用目标来说，继续投入和反复重启的成本超过了收益。

这不是证明其他人做不到，也不是宣称这个驱动所有显卡都无效。
