# 从准备到停止：实际时间线

[返回首页](../README.md) · [安装流程](02-installation.md)

日期按会话记录和 Windows 侧文件时间整理。macOS 端一度使用 America/Los_Angeles 时区，且有双系统时钟调整，所以不把不同系统日志的小时值直接当作精确先后证据。

| 时间 / 阶段 | 发生了什么 | 结果和边界 |
|---|---|---|
| 2026-10-17，准备 | Windows 识别 ADR10、8945HX、5060 Laptop，使用 NullMoth/1401 和 OpenCore 路线准备文件 | 没有从“工具支持 RTX 50”直接推导整机兼容 |
| 早期 8GB U 盘 | 能进 OpenCore，但只有 Windows，按空格没有恢复入口 | 先查设备、分区、恢复镜像、扫描策略、驱动，不重新制作整台机器的 EFI |
| 恢复镜像阶段 | 出现 `DMG has been altered` / `LoadImage Failed - Unsupported` | 后续发现旧 U 盘的镜像读取不稳定；不能靠关闭校验绕过 |
| 2026-10-18，内核早期 | 26 出现早期 type 14 Page Fault，15 恢复环境对照也曾遇到早期崩溃 | “降到 15 一定好”没有得到证实 |
| MMIO / PCI 排查 | 按本机运行时地址保留 `0xFF000000` MMIO 区域，后续启用可选 PCI hotplug 补丁 | 逐步进入恢复图形界面；单次成功不等于每个参数都有独立因果证明 |
| 输入阶段 | 菜单按键曾无响应；恢复里键盘、触控板也曾不可用 | 区分 UEFI 菜单输入、内核输入驱动和整机卡住；后期触控板可用 |
| 安装空间 | 从 D 盘预留独立空间；恢复安装器通过网线下载完整系统 | U 盘 2GiB 启动分区和内部 APFS 安装空间是两件事 |
| 首次安装自动重启 | 多次选择 `macOS Installer`；期间出现缺少 OpenRuntime 的报错 | 检查时 OpenRuntime 文件实际存在且匹配；仅刷新同版本文件，未证明根因 |
| 进入图形会话 | 黑屏只剩可移动、可摇大鼠标，之后国家选择继续转圈 | 不能因鼠标能动就认定加速正常，也不能因黑屏就判定驱动从未安装 |
| 2026-10-19，启动速度 | 原来菜单选项后约 300 秒才继续；替换匹配的 RELEASE 核心文件 | 用户明确反馈“快多了，一按就进去了”；未证明所有延迟都来自 DEBUG |
| 版本和脚本问题 | 一次恢复脚本因缺少 `shasum` 报错；有准备过但未实际完成的驱动更新 | 改为适应 Recovery 的流程；不把“包在 U 盘上”写成“已安装新版” |
| `gfxrst=4` | 在 WhateverGreen 与 NVIDIA 共存的配置里加入 | 用户反馈流畅度改善；没有由此解决所有初始化问题 |
| 2026-10-21，全面查旧 U 盘 | 无缓存重复读取 DMG，28 个位置中 22 个结果不一致；换直连接口仍有 14 个不一致 | SSD 对照全部稳定，确认读取链路异常；未定位到具体硬件部件 |
| 新 SanDisk | 建立 2GiB FAT32 MACBOOT + 剩余 exFAT；从本地原始文件复制 | DMG 28 个位置、驱动包 8 个位置抽样稳定；新盘仍卡国家选择 |
| 新盘 + 2.3.4 | 原生系统安装驱动、自动重启、收集加载版本 | 四个驱动实际加载为 2.3.4；CPU 仍只有 1 个逻辑处理器，初始化仍慢 |
| 重新尝试 26 | 用户选择用新盘重装 26，不行再考虑 15 | 只完成了新的 26 路线，没有完成 15 日用系统 |
| 恢复入口再卡住 | 上一轮误沿用已装 NVIDIA 的 IONDRVSupport Exclude 配置 | 取消恢复阶段的屏蔽，并让安装脚本在驱动安装成功后恢复；纠正的是阶段不匹配，不宣称已独立证明根因 |
| 2026-10-23，驱动状态确认 | 新日志显示原生系统的 2.3.4 安装和内核缓存构建成功 | “没有驱动”不再是可直接采用的解释；仍需看实际加载与运行 |
| 初始化绕过 | `dscl` 查询没有普通用户；恢复环境创建账户、设密码，再写入完成标记 | 脚本留下 `SETUP_SKIP_READY`；用户随后确认进入桌面 |
| macOS 端审计 | 用户安装 Codex，生成 `Hackintosh-Audit.md` | 记录 Metal/3D/部分硬件编解码测试通过，多项外设仍不完整 |
| 多核尝试 | 删除 `cpus=1`，添加 boot-args 刷新配置 | 下一次启动 Kernel Panic。不是“设置了 cpus=16”，也未证明是 Intel 显示名称导致 |
| 回退与折中测试 | 先恢复 `cpus=1`，随后按用户要求配置 `cpus=12`，给另一端审计文档追加 reply | 只确认配置落盘和语法通过，没有收到 cpus=12 的实机结果 |
| 2026-10-24，结束 | 用户删除 macOS，把空间还给 D 盘 | Windows 只读分区检查也显示旧 APFS 分区已不在，D 盘容量扩大；停止继续修复 |

## 特别容易写错的历史

1. 进过 15 恢复环境，不等于装好了 15。
2. 先前下载过 2.4.3，不等于本机成功运行了它。
3. 新盘读镜像稳定，不等于新盘解决了全部卡顿。
4. 修复了不合适的配置项，不等于找到了每次 PCI 卡住的唯一根因。
5. 绕过初始化进桌面，不等于完整修好了初始化服务。
6. 去掉 CPU 限制后 Panic，不等于已经定位为 TSC、核心数补丁、网络驱动或 GPU 中的某一个。
